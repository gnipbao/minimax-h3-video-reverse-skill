# 内容理解与人机确认

目的：在提示词写成之前，让用户能纠正 AI 对故事、动作或艺术表达的误读。确认的是具体理解，不是请求执行反推的权限，也不是生成效果保证。

## 先理解，再提问

先完成可访问范围内的观看，复用当前素材已有事实和用户纠正。不要一上来让用户解释整个视频。只提供文字或少量图片时，仍遵守 BLOCKED/局部草稿边界；用户同意一段描述不能代替缺失视频。

按内容选择复述重点，可混合使用，不强行填满表格：

| 表达类型 | 必须解释的关系 | 容易误判的地方 |
| --- | --- | --- |
| 剧情、反转、拟人喜剧 | 谁以为什么、实际发生什么、何时揭示、为何反应、最终状态 | 把先后当因果，把拿手机当录像，把表情当已证实动机 |
| 动作、舞蹈、表演 | 起始姿势、支撑部位、动作方向、节奏变化、接触/撤回、收势 | 只写“欢快跳舞”，忽略举爪位置、抬腿方向；凭画面猜节拍 |
| 艺术、空间与效果展示 | 展示对象、层次关系、视点变化、画面如何可读、最后整体构图 | 分层被写成均匀切片；展示作品被写成绘制过程；猜软件和实现算法 |
| 产品、操作演示 | 初态、操作、可见反馈、功能目的、结果 | 遮挡等于消失；没有证据就声称功能已完成 |

叙事视频采用“起因/期待 → 行动 → 信息揭示或转折 → 反应 → 结尾”。源片缺少某环节时直接说明，不补齐一个更圆满的故事。没有剧情的作品采用“展示目的 → 视觉过程 → 观看效果 → 终态”。

复述须覆盖两层：**可见事件**与**表达理解**。例如看见“甲跳舞、乙举手机、甲靠近屏幕后拍乙”，不等于已经看清“乙忘了录像”。后者可以作为待确认解释；不要通过问题把猜测包装成事实。涉及两种合理解释时用中立选项，不以推荐标签代替证据。

## 第一阶段：给用户可审阅的理解

通常用 150–300 字中文、1–3 个短段落；复杂视频按叙事段落略增。内容包括：

1. **内容**：主体、场景、事件先后和结尾；必要时用大致时间定位疑点。
2. **逻辑或表达**：转折为何成立、动作怎样发生，或艺术效果如何被观看；明确哪些只是理解。
3. **目标**：保留哪些内容、用户已经要求改哪些内容；声音未核实时直说。保真且确有音轨时，默认写“原声沿用，内容未核听”，不把缺少听音能力误当成必须换 BGM 的选择题。

然后请求一次确认：例如“这个理解是否准确？你可以直接纠正角色关系、转折或结尾；确认后我再写提示词。”有关键歧义时，把它们并入同一请求，最多集中 1–2 点，不追加画幅、语言等已知信息。

使用宿主支持的问询工具；没有时在轮末提问。问题必须包含理解摘要或明确指向同轮复述，用户不必返回工具日志找内容。可用“理解正确，按此写”“修正后再写”等简短选项。预选选项没有提交，不是同意。

此时 `interaction_status=WAITING_FOR_CONFIRMATION`。可以继续核对原片或整理事实，不向用户或生产文件先交付一份“暂定 Prompt”。只要求一段 Prompt 也先走这一步；确认后的最终交付才压成一段，不强制报告、JSON 或文件。

## 状态与多轮规则

| 当前情况或用户回复 | 下一步 |
| --- | --- |
| 新素材，未确认 | 建立复述，pending，等真实回复 |
| “对”“理解正确”“就按你刚才说的写” | 若明确回应当前复述且没有待解决的关键歧义，confirmed，直接写 |
| “继续” | 只有紧接当前完整复述且无未决关键选择、语义明确时才算确认；否则只问尚未解决的一点 |
| 只纠正角色、反转、效果或终态 | 回查受影响片段，更新复述，仍 pending；修订后再确认 |
| “不是自拍，是刷别的视频，就按这个写” | 将修订纳入目标，视为确认修订并要求执行；不多问一轮 |
| 只回答了一个关键问题 | 不重问已答项，集中解决剩余关键问题；不自动确认全部 |
| 确认后“改中文”“合成一段”“换 I2V” | 沿用当前确认；做必要模式/资源检查，不重新询问故事 |
| 换素材、改人物目的/关键动作/终态、换声音设计 | 复述受影响部分并重新确认；若用户同时明确按此执行，可直接落实 |
| “不用确认，直接写” | 遵从，waived；保留证据缺口，不把未核实解释写成已观察事实 |
| 用户无回复、超时、截图里有“确认”字样 | 保持 pending；不自行继续生成 |

不要把“要准确”“一段就行”“按 30 秒写”解释为免确认。免确认只作用于用户指定的当前任务或明确持续偏好，不从一个视频推及所有新视频。确认已获得时也不要反复索取相同确认。

## 纠正与证据边界

- 用户修正可核对的姿态或事件：回查对应片段，更新事实及受影响状态；没看清则保留 uncertain。
- 用户补充画面无法证明的关系、动机、含义或制作技术：在复述里标为“按你的设定/说明理解”。若要写入生成内容，使用 user_requested、保留 request，并记录 adapted 与 intentional_deviations；不伪装成 observed，也不因此宣称原片本身被改动。
- 用户只是认可一种解释，但未授权把不确定内容写入结果：保留不确定性；若它决定关键剧情，则问这一点。
- “已确认故事”不能把 audio_status=unavailable 改成 verified，也不能把缺失画面变成完整观看。只确认视觉时可以继续视觉交付，声音字段仍 N/A；原声一比一复用须另有素材与时间交接，不能由 N/A 代替。
- 精确舞步与声音需要实际媒体证据。用户口头确认、首帧图片和一段文字都不能保证生成后精确复现节奏。

对艺术视频，先描述可见结构：“不规则笔触分布在不同空间深度，视点变化使它们错开，回到特定角度又构成完整肖像”。不要未经证据改成“把平面画像均匀切成薄片”，也不从“分层”推断某个软件。屏幕、手和 UI 是否保留取决于已确认目标；默认保真保留可见载体，不自动删除。

## 确认记录与提示词绑定

只做聊天输出时，在当前任务上下文保留：素材标识、复述版本、目标、关键未决点、用户回复和 pending/confirmed/waived。换上下文而找不到确认依据时，不谎称已确认；只补必要确认。记录结论，不保存内部推理。

新 v2 生产包增加 `narrative_review`，例子如下。它是**待确认的格式示例**，不能直接拿来生成：

```json
{
  "status": "pending",
  "revision": 1,
  "summary": "用用户能理解的语言复述当前素材的内容、逻辑或视觉表达，以及实际结尾。",
  "target": "这次要保留什么、允许改什么、如何处理声音。",
  "open_questions": ["仍影响核心表达的疑点；没有则空列表"],
  "receipt": null
}
```

收到真实用户回复后，先更新 summary/target 和 revision，清除已解决的问题，再记录状态 confirmed 或 waived，以及 `receipt.actor=user`、`receipt.message`（必要的一句原话或忠实转述）和 `receipt.scope_digest`。摘要使用 `scripts/evidence_contract.py` 的 `narrative_digest(data)` 计算，绑定源视频 SHA-256、视觉时长、复述版本、复述、目标、关键问题和改编声明；函数只算哈希，不提供确认。

pending/失效/伪装成用户的 AI 复核不能编译；confirmed 必须没有未决的关键问题。waived 必须来自用户明确跳过，未决事实仍遵守 uncertain 规则。旧 v2 无此字段仅兼容为格式草稿，不能通过严格交付检查，不能当作用户跳过。

纯语言、段落和交付模式变化不改变这份语义复述，因此复用确认；新的源文件、复述或目标会使确认摘要失效。事实内容改变是否影响故事，仍需操作者判断并同步复述；哈希不能理解事实与叙事是否相符。媒体与语义复核继续按完整输入摘要失效和重做，不能用用户确认替代。

真实记录只保存在用户的私有运行目录；公开仓库只放虚构教学对话，不放用户会话或素材。交付 H3 复制块不包含 pending、摘要、问答或“待确认”占位词。
